# 为什么要这样开发：把 AI 的能力用在 SoC 上

开发一个 SoC，有很多时间花在写代码之外。刚理清一个模块，又要切换到工具链；启动
一场仿真，还要记得回来查看；发现问题后，又得把来龙去脉重新讲给下一位接手的人。
这些事情都需要人的注意力，而且经常打断真正需要思考的架构问题。

我们希望借助 AI 改变这件事：

**人专注架构取舍与验收；AI 通过快速继承上下文、并行推进与持续执行，减少人的注意力与交接负担。**

具体来说，我们先把希望用到的能力归纳成三项：**身外化身、超绝专注力、超绝持久力**。
OpenCUTE 要做的，就是为这些能力准备好可以工作的工程环境，让它们真正参与 SoC
的构建、调试和增量开发。

## 第一项：parallel身外化身，让可以并行的工作同时推进 {#parallel}

假设已经确定要增加一种运算，输入输出、数值规则和指令含义也已经说清楚。接下来，
RTL 需要实现它，SDK 需要提供调用方式，reference 需要给出预期结果，测试需要覆盖
边界情况。这几件事有共同的前提，也有可以同时开展的部分。

支持多 agent 的执行环境可以把已确认的上下文与 Truth 交给多个 subagent：
一个处理 RTL，一个处理 SDK，一个准备参考结果和测试。每个 agent 从同一份约定
开始，集中解决自己的问题，不用让人反复从头解释整个仓库。

这里最有价值的是**复用已经想清楚的部分**。目标是什么、接口在哪里、哪些决定已经
敲定、怎样算完成，都应该能被交接。只说一句“你做硬件，你做软件”，两个 agent
仍可能对同一条指令形成不同理解。

所以，并发之前先确定依赖和修改范围：各 agent 尽量维护各自负责的文件；共享接口
由明确的任务负责更新；依赖尚未确定的工作等到前置结果交付后再开始。各部分完成后，
还要有人或负责集成的 agent 把它们接起来，验收组合后的行为。

对应到 OpenCUTE，这需要 [任务拆分](decomposition.md)、[组件接口](modules.md) 和
[统一事实来源](config-architecture.md#single-truth)。有了这些，增加 agent 才有机会变成增加有效产出。

## 第二项：attention超绝专注力，持续观察正在发生什么 {#attention}

仿真启动之后，人通常不会一直盯着终端。过一会儿回来，才发现任务已经报错，或者
程序一直在重复某段行为，刚才的等待并没有带来有用结果。

我们希望 AI 能通过工具定时观察，例如每 **10 秒**读取新增日志、进程状态和检查器
输出，持续回答一个具体问题：**这次实验现在进行到哪里，还值得继续等吗？**

| 观察到什么 | 可以继续做什么 |
|---|---|
| 编译从 elaboration 进入 C++ 构建 | 更新当前阶段，让人知道构建仍在推进 |
| 仿真周期、请求/响应或任务完成数增加 | 结合预期进度判断是否正常，而不只看进程是否存在 |
| checker 报告首个数值或协议错误 | 保留现场，停止已确定无效的本次测试，开始定位 |
| 一段时间没有新输出 | 结合进程、预算和更细的观测继续判断；安静不一定是卡死 |

AI 可以帮助解释和追踪这些变化，确定性的检查交给工具。比如数百万条访存记录的
配对和逐字节比较，应由 checker 持续完成；AI 读取其结论，关联源码与日志，判断
下一步该查哪里。这样才不会让人的注意力消耗在重复观察上。

这里的“每 10 秒”是一种可设置的观察节奏，需要运行中的调度工具配合。OpenCUTE 的
系统 runner 已有在线 trace 检查和首错停止，可以用 `--poll-seconds 10` 设置向
checker 输送新增记录的间隔；AI 定期分析日志则是上层开发流程，两者各有职责。
当前默认间隔仍为 60 秒。实际操作见 [在线联合检查](demo/online.md)。

## 第三项：persistence超绝持久力，围绕同一个目标连续工作 {#persistence}

一个问题经常不会在第一轮就解决。可能先是编译失败，修好后遇到输出不符，再往下查
发现等待条件有问题，最后还要重新构建和回归。对人来说，每次中断再回来，都要重新
找回刚才的思路。

我们希望用 **goal 模式**组织这样的工作：明确目标后，让 AI 反复执行
“观察结果 → 找到问题 → 修改 → 验证 → 选择下一步”，在工具允许的执行时段和预算内
持续推进。它不需要人每完成一个小动作就再说一次“继续”，也不受人的疲劳节奏影响。

例如，目标是“让 BERT 第一阶段在选定平台上通过完整验证”。AI 可以先检查环境，
再构建程序、校准 golden、运行 RTL，遇到错误就定位并修复，直到所有输出和结束条件
都通过。每轮的输入、尝试和结果留下记录，下一轮沿着已有判断继续。

如果目标是优化，还要先说清楚优化什么。可以要求“在正确性不退步的前提下降低周期数”，
同时限定候选配置、运行次数或时间预算。持续工作才有明确方向，也知道什么时候应该
交付当前最好的结果，或者把需要架构取舍的问题交回给人。

目标与进度记录要随着每轮工作保存。换一个 agent 或恢复执行时，能够读到已经尝试的
方案和失败原因，才不会把“持久”变成反复重做同一件事。

goal 模式依赖开发环境提供持续调度、上下文恢复和进程管理。当前 OpenCUTE 提供构建、
运行与验收工具，统一的 AI 目标调度器仍是待接入能力。我们先把每次任务的输入和交付
整理清楚，让它能够被这样的执行环境接手，具体见 [增量交接](config-architecture.md#task-brief)。

## 人把精力留在哪些地方

人需要决定做什么样的系统、为什么值得做、哪些代价可以接受。例如，为了吞吐增加
缓存和并发度是否值得，为了面积减少某项能力是否可以，哪些误差在业务上能够接受。
这些决定确定了 AI 的工作方向。

AI 可以在这个方向内准备候选方案、修改实现、持续跑实验，并把结果整理成可比较的
证据。人验收时关心的是：原本的目标是否实现，代价是什么，还有哪些条件没有满足。
工程细节应当能够向下追查，但不要求人始终守在每个构建和测试旁边。

## 接下来，自然语言和硬件工具之间还缺什么 {#translation}

现在可以回到最初的愿望：“让 AI 帮我构建一个能运行这个Qwen模型的 SoC。”
这句话足以开始讨论，却还不足以启动硬件工具。哪个模型阶段、什么数据格式、多少核、
怎样的内存、怎样判断结果正确，都需要继续明确。

自然语言适合表达目的，硬件工具需要参数和约束。OpenCUTE 要接上的，就是中间这段
逐步具体化的过程：

| 我们先说的话 | 还需要确定什么 | 最后交给工具什么 |
|---|---|---|
| “先让这段计算跑对” | 输入、数据布局、数值规则和输出范围 | SDK 程序、case 和 reference |
| “用这样的系统运行它” | CPU、向量与矩阵部件、内存和执行策略 | HWConfig 及其引用的配置 |
| “确认它确实完成了” | 观察哪些事件，何时比较，怎样认定正常结束 | trace 接口、checker 和验收条件 |

配置把系统选择固定下来，各子项目把小愿望落实为实现，检查器告诉我们结果是否成立。
这就为三项能力提供了共同基础：subagent 能继承同一份 Truth，持续观察有明确的信号，
持续执行有明确的目标和完成条件。
